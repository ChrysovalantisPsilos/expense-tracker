# Translating Budgeer (i18n)

Budgeer is being translated into Greek, one feature at a time. This page sets
the conventions, so that several people can translate different features in
parallel without conflicts. Greek wording, tone and terms are in
[`i18n-glossary-el.md`](i18n-glossary-el.md).

## How it works

| Piece | Where |
| --- | --- |
| Engine (pure: lookup, fallback, `{{vars}}`, plurals, rich-text parser) | `src/shared/lib/i18n/translate.js` |
| Active language, the plain `t()`, `intlLocale()` | `src/shared/lib/i18n/i18n.js` |
| Language preference (device detection, profile sync rules) | `src/shared/lib/i18n/language.js` |
| React: `LanguageProvider`, `useT()`, `<Trans>`, `useLanguage()` | `src/shared/lib/i18n/I18nProvider.jsx` |
| Profile ↔ device sync (signed in) | `src/shared/lib/i18n/ProfileLanguage.jsx` |
| Dictionaries | `src/locales/{en,el}/<namespace>.js` |
| Parity tests | `test/i18n.test.js` |

We use a small in-house engine rather than i18next + react-i18next. The
reasons are in the header of `translate.js`: Budgeer needs about 150 lines of
features, and the libraries would add around 20 KB gzipped.

- **Languages:** `en` (the source and the fallback) and `el`.
- **Loading:** English is bundled with the app. Greek is its own chunk,
  loaded before the first render on a Greek device (`bootLanguage()` in
  `main.jsx`), so the app never flashes English first.
- **Preference:** Settings › Language offers "Follow my device" (the
  default), English and Ελληνικά. Signed out, the public header has an
  EN / ΕΛ switch. The choice is stored in `localStorage`
  (`STORAGE_KEYS.language`) and, signed in, in `profiles.language`
  (0091: `'en' | 'el' | null`, where null means follow the device). On a
  signed-in load the profile's language wins. When the profile has none, a
  choice made on this device is saved up to it. The shared demo account keeps
  its choice on the device only.
- **Switching:** changing the language remounts the app (`LanguageBoundary`),
  so everything re-renders, including components that only format numbers.
  `<html lang>` follows the language. That also makes CSS
  `text-transform: uppercase` drop Greek accents correctly (ΡΥΘΜΙΣΕΙΣ, not
  ΡΥΘΜΊΣΕΙΣ).
- **Fallback:** a key missing in Greek shows the English string. In
  development it also logs `[i18n] el has no "ns:key"` once. A key missing
  everywhere shows `ns:key`.

## Namespaces

There is one namespace per feature, in one file per language:
`src/locales/en/groups.js` and `src/locales/el/groups.js`. Every namespace
already exists, with the untranslated ones as `export default {}`, and is
registered in both `index.js` files. A translator therefore only edits their
feature's two files and never the shared index, so parallel work doesn't
conflict.

| Namespace | Covers |
| --- | --- |
| `common` | Shared words (`actions.logIn`, `errors.notSaved`) and everything in `src/shared/ui` |
| `shell` | `src/app`: the app shell, navigation, More |
| `<feature>` | `src/features/<feature>` (auth, backup, budgets, categories, dashboard, groups, help, import, insights, landing, notifications, onboarding, privacy, recurring, savings, settings, transactions, whatsnew) |

A string that two features need goes in `common`. It is never copied into
both (CLAUDE.md #3).

## Keys

- Keys are nested objects with camelCase segments, grouped by screen or
  component and then by element: `settings:appearance.title`,
  `groups:settle.confirm.body`, `landing:how.invite.copied`.
- Name a key for what the text *is*, not for what it says: `title`, `lead`,
  `empty.body`, `actions.save`. Never `clickHereToSave`.
- Rows of a list share a shape: `rows.<id>.label` and `rows.<id>.desc`. The
  code keeps an `id` in its table and builds the key: ``t(`rows.${id}.label`)``.
  Keep literal ids in the tables (`tour: 'nav-groups'` stays as it is;
  `test/tourSteps.test.js` reads them).
- Only add a key when a string exists. Remove the key when its string goes
  (CLAUDE.md #7).

## Using strings

```jsx
import { Trans, useT } from '../../shared/lib/i18n/I18nProvider.jsx'

export default function SettleCard({ name, amount, count }) {
  const t = useT('groups')                      // default namespace
  return (
    <>
      <Heading>{t('settle.title')}</Heading>                     {/* groups:settle.title */}
      <Text>{t('settle.owes', { name, amount })}</Text>          {/* interpolation */}
      <Text>{t('settle.payments', { count })}</Text>             {/* plural */}
      <Button>{t('common:actions.save')}</Button>                {/* another namespace */}
      <Trans t={t} k="settle.terms"
        components={{ link: <Link as={RouterLink} to="/terms" /> }} />
    </>
  )
}
```

```js
// src/locales/en/groups.js
export default {
  settle: {
    title: 'Settle up',
    owes: '{{name}} owes you {{amount}}',
    payments_one: '{{count}} payment settles everyone',
    payments_other: '{{count}} payments settle everyone',
    terms: 'Payments follow the <link>Terms of Use</link>.',
  },
}
```

- **Components** use `useT(namespace)`.
- **Code outside React** (data modules, helpers that build toasts or
  labels) uses `import { t } from '…/shared/lib/i18n/i18n.js'` with a full
  `'ns:key'`. Call it when the text is needed, inside a function. At module
  load it would be frozen in English. A table of labels at module level
  holds keys, not strings.
- **Interpolation:** `{{name}}`. Pass values that are already formatted
  (money through `formatMoney`, dates through `dates.js`). Never build a
  sentence by gluing translated pieces together, because word order differs
  between languages. Put the whole sentence in one key with placeholders.
- **Plurals:** give `key_one` and `key_other` (the forms
  `Intl.PluralRules` asks for: `one`/`other` in both English and Greek), and
  call `t('key', { count })`. Every form shows `{{count}}`.
- **Rich text:** mark the parts with tags (`<link>…</link>`, `<strong>…</strong>`,
  self-closing `<br/>`) and map each tag to an element with `<Trans>`. The
  string is parsed into a tree and never injected as HTML (CLAUDE.md #5: no
  `dangerouslySetInnerHTML`). The Greek string must use the same tags as the
  English one; the test checks this.
- **Formatting:** don't hard-code a locale. Use `formatMoney`, `formatRate`
  (`currency.js`) and `monthTitle`, `monthName`, `shortMonth`, `shortDate`,
  `shortDateTime` and `lastMonths` (`dates.js`). For anything else, pass
  `intlLocale(<the English locale used before>)` to `Intl` or
  `toLocale*String`. That keeps English exactly as it was and gives Greek
  `el-GR` (`1.234,56 €`, `26 Σεπ 2026`, `Σεπτέμβριος 2026`). Greek
  month-only headings need the nominative form, so use `monthName()`, not
  `toLocaleDateString('el', { month: 'long' })`, which returns the genitive
  "Σεπτεμβρίου".
- **Brand names and data** stay as they are: Budgeer, IBAN, Revolut, PayPal,
  currency codes, and user-entered names and descriptions.

## Adding a string

1. Add the key to `src/locales/en/<ns>.js`.
2. Add the same key to `src/locales/el/<ns>.js`, with the Greek from the
   glossary's terms and tone. If you can't translate it yet, don't add a
   placeholder: the test requires identical keys, so the string waits in
   English until both languages exist.
3. Use it through `useT` / `t` / `<Trans>`.
4. Run `npm test` (`test/i18n.test.js`: same keys, same `{{placeholders}}`,
   same tags, every plural form) and `npm run lint`.
5. Check the screen in Greek at phone width. Greek runs 20–30% longer than
   English, so look for clipped buttons, tabs and one-line labels.

## Converting a feature (a later phase)

1. Take the namespace for your feature (e.g. `groups`). Work only in
   `src/features/groups/**` and `src/locales/{en,el}/groups.js`. For a word
   that belongs in `common`, coordinate: `common.js` is the one shared file.
2. Move every user-facing string into keys: JSX text, `aria-label`, `title`,
   `placeholder`, `alt`, toasts, confirm dialogs, validation messages, empty
   states, and labels built in the feature's `.js` modules.
3. Keep pure maths pure. A `*Math.js` returns data or keys, and the component
   translates them. When a unit test asserts English text, keep the English
   output identical, since node tests run in English.
4. Add the feature's files to the `react/jsx-no-literals` block in
   `eslint.config.js`, so the lint keeps them clean from then on.
5. Screenshot the feature in Greek and English, at phone and desktop sizes.

### The rule: no user-facing literal in JSX

In a converted file, every word a person reads comes from a key. The
`react/jsx-no-literals` rule enforces this for the converted files listed in
`eslint.config.js`. Symbols and the brand may stay literal (`·`, `—`, `©`,
`Budgeer`); a URL or a code goes in a named constant. Once every feature is
converted, **the last step is to change that block's `files` to
`src/**/*.jsx`**. It is limited to the converted files for now, because
turning it on everywhere today would fail lint (`--max-warnings 0`) on every
file not yet translated.

## Server texts (later phases)

The server doesn't render the app, so it can't use `src/locales`. Instead:

- **Language:** `profiles.language` (0091). Null means the user follows
  their device; the server then uses English (it can't see the device).
  Settings › Language writes the column on every change, and a signed-out
  choice is saved on the next sign-in.
- **Emails** (`supabase/functions/*` and `_shared/*Emails.ts`, auth email
  templates): move each template's strings into a
  `supabase/functions/_shared/i18n/{en,el}.ts` dictionary with the same key
  and placeholder conventions. Add a tiny `tr(lang, key, vars)` in `_shared`
  that falls back to English. Keep HTML escaping where it is (escape the
  *values*, never the template), and pick the language from the recipient's
  profile, not the sender's. Supabase Auth's own emails (confirm, reset) are
  templates in the dashboard and can't vary per user. Make them bilingual
  (Greek line + English line) or send them through the hook, if it is
  enabled.
- **PDF / Excel statements:** these are now made on the device, not by the
  server (`generate-report` and `group-report` stay one release only as a
  fallback). Every word on them is in one object,
  `supabase/functions/_shared/statementText.ts` (`STATEMENT_TEXT`), which
  the builders take as an argument (`loadStatement`, `statementBytes`,
  `groupStatementPdf`, and the note helpers in `statementMath.ts`). To translate them, build an object of the
  same shape from `t` in the active language (a `statements` namespace) and
  pass it from `deviceStatement.js` / `deviceGroupStatement.js`. Amounts
  (`money`, `fmtMinor`) and dates are still English-formatted and need
  `Intl` with `el-GR` then. The PDF already draws Greek letters (DejaVu Sans
  is the toolkit's Unicode fallback).
- **Push notifications and in-app notifications:** today the SQL writes
  English `title`/`body` into `notifications`. Store a `type` and parameters
  (it already stores `type`), and render them on the client (`notifications`
  namespace) and in the push sender (`_shared/i18n`) in the recipient's
  language. Don't store translated text in the database.
- **SQL error messages** (e.g. "Remove the other members before deleting
  this group."): keep raising stable English messages. The client maps known
  messages or error codes to keys (`shared/lib/errors.js` → `common:errors.*`),
  and anything unknown falls back to the generic message. Changing a message
  in SQL means changing its client mapping and the db test that matches it,
  in the same change.
- **Legal pages:** the Privacy Notice and Terms get a Greek copy, with a line
  saying the English version prevails. Until then the Terms quote their
  disclaimer in English (`translate(…, { lang: 'en' })` in `Terms.jsx`).

## Fonts

The bundled Poppins and Nunito Sans subsets are Latin only, so Greek text
renders in the theme's system fallback font. If the owner wants a matching
Greek typeface, add a font that has a Greek subset (e.g. `@fontsource/*`
`greek-*.css`) as a separate change and check the bundle size.
